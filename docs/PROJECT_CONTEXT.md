- **Purpose & users** — Built an analytical data platform for NYC TLC yellow-taxi trip data serving analysts and an ML pre-trip fare estimation workflow, spanning ingestion through dashboard consumption; evidence: `taxi` CLI (`src/taxi/cli.py`) with 15 subcommands as the single entry point, 37 Python modules across 10 packages under `src/taxi/`, 5,759 LOC.
- **System architecture** — Implemented a layered pipeline (acquisition → ingestion → validation → marts → metadata → ml → benchmark) as an installable package with a declarative config/contract layer separated from logic; evidence: `pyproject.toml` package `nyc-taxi-platform`; `contracts/trips.yml` declares 27 columns and drives all downstream schema/validation/ML-role decisions with no hardcoded values in modules.
- **Data model & persistence** — Designed a partitioned Parquet lake (raw → clean/rejected → marts → features) plus an append-only metadata ledger, using DuckDB 1.5.4 as the query/transform engine with atomic file writes; evidence: `MetadataStore` (`src/taxi/metadata/store.py`) twin-writes Parquet+CSV per table via temp-file + `os.replace`; 9 SQL-defined marts under `src/taxi/marts/sql/` plus a `dim_zone` dimension.
- **Core workflow / business logic** — Implemented a data contract that compiles per-column validation rules into a single SQL pass and classifies every column's ML role (target/feature/excluded) to prevent leakage by declaration; evidence: `src/taxi/validation/rules.py` `bind_params()` and `src/taxi/contract.py` `MLRole` enum consumed by `src/taxi/ingestion/pipeline.py`; contract version tracked via `contract_fingerprint` (e.g. `1.0.0+be8b35e8b06fd716`) recorded per run.
- **Interfaces & feature coverage** — Built an 8-page Streamlit dashboard (Overview, Demand, Revenue, Zone, Flows, Tips, Data Quality, ML Fare Prediction, Benchmarks), 799 LOC, restricted to reading only marts/metadata; evidence: `dashboard/_data.py` `read_mart()` allow-lists `data/marts` paths, enforced by `tests/integration/test_dashboard_reads_marts_only.py`.
- **Data volume & scale** — Ingested and validated a full 12-month yellow-taxi year end to end, not a single sample month; evidence: 48,722,602 raw rows across `data/raw/yellow/yellow_tripdata_2025-{01..12}.parquet` (3.18M–4.59M rows/month) resolved to 44,157,407 clean + 4,565,195 rejected rows (9.37% full-year rejection rate) in `data/clean` and `data/rejected`, both hive-partitioned by `year=/month=`.
- **Mart & feature output at scale** — Built all 9 registry-defined marts across all 12 partitions and a matching feature table sized to the full clean layer; evidence: `mart_builds` ledger shows 108 build records (9 marts × 12 months); `mart_od_pairs` holds 455,471 origin-destination rows, `mart_daily_revenue` holds exactly 365 daily rows; `data/features` totals 44,157,407 rows, matching the clean layer 1:1.
- **Performance & scalability** — Implemented incremental, partition-scoped mart rebuilds (`incremental_by_month` vs `full` refresh) and a benchmark suite (label `full-2025`) comparing mart reads against full-year clean-layer DuckDB scans across 9 workloads; evidence: measured speedups from the `benchmarks` ledger — `dashboard_overview` 0.1363s → 0.0030s (45x), `fare_distance_profile` 0.4944s → 0.0026s (190x), `top_od_pairs` 0.2380s → 0.0148s (16x) — with identical `result_fingerprint` between mart and clean-layer answers on every query.
- **ML modeling & measured results** — Trained and evaluated 4 models (median baseline, grouped baseline, linear regression, HistGradientBoosting) per product variant under a strict temporal split (train 2025-01..09, validation 2025-10..11, test 2025-12), using reservoir-sampled training (400,000 rows/month, `configs/settings.yml: train_sample_rows_per_month`) but full-row evaluation; evidence: `ml_evaluations` ledger — 3.6M-row training set, evaluated on the full 7,586,183-row validation span and 4,049,013-row test month; best test MAE 9.58 (origin_only) and 4.92 (destination_known, R²=0.72) vs. grouped-baseline MAE 9.73/higher; 1,112 rows of segment-level error breakdown (`ml_segment_errors`).
- **Reliability & testing** — Implemented reconciliation via an order-independent XOR/SUM row fingerprint (`fingerprint()` in `src/taxi/core/duck.py`) and a temporal train/validation/test split with an explicit leakage guard for ML; evidence: 116 automated tests collected (1,338 LOC) across `tests/unit` (7 files), `tests/data_quality` (5 files), `tests/integration` (5 files), `tests/ml` (3 files, including `test_no_leakage.py`).
- **Data quality & anomaly detection** — Implemented a rejection taxonomy of 9 named reasons with per-row primary-reason attribution surfaced on a dedicated dashboard page; evidence: full-year rejection breakdown (`data/rejected`, 4,565,195 rows) with the December 2025 partition itemized in the `reconciliation` ledger — `NON_POSITIVE_DISTANCE` 152,656, `NEGATIVE_TOTAL_AMOUNT` 48,869, `NEGATIVE_FARE` 48,175, `NON_POSITIVE_DURATION` 58,021, `IMPOSSIBLE_SPEED` 1,150 rows.
- **Security & operational safety** — Centralized all filesystem path construction through one `Paths`/`Settings` object and used list-argument `subprocess.run` (no shell) for a `git describe` version stamp with a 5-second timeout and source-hash fallback; evidence: `src/taxi/config.py`, `src/taxi/core/hashing.py`; explicit limitation — no CI pipeline, no Dockerfile, and no dependency lockfile are present in the repository.
- **Code quality & conventions** — Enforced module-level design-rationale docstrings, `from __future__ import annotations` typing, and fail-closed error handling (unbound `${param}` tokens raise `KeyError`, invalid temporal splits raise `ValueError` in `__post_init__`); evidence: Ruff configured at 100-char line length/py310 target in `pyproject.toml`; no other linter/formatter config present.
- **Delivery process & escalation** — Diagnosed and fixed a production-shaped defect where a shared-directory Parquet cleanup routine deleted sibling metadata ledgers on every write; evidence: root-caused to `target.parent.glob("*.parquet")` in `src/taxi/core/duck.py`, scoped the fix to `f"{target.stem}*.parquet"`, then recovered 8 affected ledgers from their CSV mirrors, verified via `st.cache_data` invalidation and process restart.
- **Known limitation — audit-trail gap (found during this review)** — The per-run lineage ledgers do not cover the same 12-month scope as the data itself: `pipeline_runs`, `reconciliation`, and `source_manifest` each hold exactly 1 row (the most recent December run) despite `mart_builds` (108 rows) and `partition_state` (12 rows) confirming all 12 months were actually processed; evidence: direct row counts via DuckDB against each `data/metadata/*.parquet` file — 11 months of run-level audit history are unrecoverable, a residual effect of the same shared-directory Parquet-overwrite bug fixed above, predating that fix.
- **Delivery maturity & strongest evidence** — Shipped a working, independently-runnable pipeline reproducible without network access, with documentation kept in sync with the contract by an automated check; evidence: `Makefile` `demo` target running the full pipeline on synthetic data, `taxi report` regenerating `docs/generated/EVIDENCE.md`, and `tests/unit/test_docs_match_contract.py` failing the build if docs drift from `contracts/trips.yml` (27 columns tracked).
